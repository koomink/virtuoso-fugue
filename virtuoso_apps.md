# Virtuoso Apps

Virtuoso apps are external strategy packages. They propose candidate
instruments, data needs, and target allocations through `maestro.sdk`; Maestro
owns DataHub access, universe approval, signal validation, portfolio
construction, risk, operator approval, execution, state, and audit.

This document is the implementation guide for Virtuoso app developers and for
wrapper authors adapting an existing strategy repository to Maestro.

## Core Rule

Strategy-specific code belongs in the app repository, not in Maestro core.
Maestro owns only the SDK contract, plugin loader, orchestration pipeline, and
scaffold generator.

A Virtuoso app must treat `maestro.sdk` as its only Maestro dependency. Do not
import Maestro broker, execution, state, orchestration, approval, Telegram, KIS,
DataHub, portfolio, risk, or config internals.

## Development Workflow

Start from the scaffold unless there is a specific reason to hand-build the app:

```bash
maestro init-virtuoso-app \
  --output ./my_app \
  --package-name my_virtuoso_app \
  --class-name MyVirtuosoStrategy
```

By default, the strategy id is the package name. Use `--strategy-id` when the
configured Maestro strategy id should differ. Existing output paths are refused
unless `--force` is passed.

The generated package contains:

- `pyproject.toml` using setuptools and Python `>=3.11`
- `README.md` with the app boundary and config snippet
- `src/<package_name>/__init__.py`
- `src/<package_name>/strategy.py`
- `tests/test_strategy_contract.py`

Install Maestro and the app into the same runtime environment:

```bash
uv pip install -e /path/to/Maestro
uv pip install -e ./my_app
```

Configure the app by entrypoint string:

```yaml
strategies:
  - id: my_virtuoso_app
    enabled: true
    mode: paper
    weight: 1.0
    entrypoint: "my_virtuoso_app.strategy:MyVirtuosoStrategy"
    config:
      symbols: ["SPY", "CASH"]
      allocations:
        SPY: 0.6
        CASH: 0.4
```

## Recommended Repository Structure

Put the Virtuoso wrapper inside the strategy or app repository, not inside the
Maestro repository. This keeps strategy-specific code, upstream strategy
updates, wrapper changes, and app-specific dependencies reviewable in one repo
and one pull request.

Recommended layout when adapting an existing GitHub strategy repository:

```text
github-strategy-repo/
  ├── pyproject.toml              # upstream strategy dependencies live here
  ├── original_strategy_code/
  └── virtuoso_adapter/           # generated by maestro init-virtuoso-app
      ├── pyproject.toml          # optional separate adapter package metadata
      ├── README.md
      ├── src/virtuoso_adapter/
      │   ├── __init__.py
      │   └── strategy.py         # BaseStrategyPlugin implementation
      └── tests/
          └── test_strategy_contract.py
```

The scaffold uses the Python `src` layout by default. If the strategy repo
already uses a flat package layout, either keep `virtuoso_adapter/` as a
separate installable package or move `src/virtuoso_adapter` into the repo's
existing package layout and update package discovery in `pyproject.toml`.

Heavy dependencies such as LangChain, LLM provider SDKs, vector databases, model
runtime packages, and upstream strategy libraries belong in the strategy/app
repo only. Do not add them to Maestro core unless Maestro itself directly owns
that integration.

## Loader Contract

Maestro loads each enabled strategy from `strategies[*].entrypoint`, which must
use `module:ClassName` format.

The loader currently enforces:

- the entrypoint imports successfully
- the class can be constructed with no arguments
- the constructed object is an instance of `BaseStrategyPlugin`
- `plugin.manifest().strategy_id` exactly matches `strategies[*].id`
- `plugin.manifest().result_type` is `target_allocation`
- `plugin.manifest().sdk_contract_version` is at or below Maestro-supported
  contract version `1.0`

If any condition fails, Maestro raises a plugin load error before the strategy
runs.

## SDK Interface

A strategy plugin implements `BaseStrategyPlugin`:

```python
class BaseStrategyPlugin(ABC):
    def manifest(self) -> StrategyManifest: ...
    def build_data_requests(self, context: StrategyContext) -> list[DataRequest]: ...
    def build_candidate_requests(
        self,
        context: StrategyContext,
    ) -> list[CandidateInstrumentRequest]: ...
    def run(self, data_bundle: DataBundle, context: StrategyContext) -> StrategyResult: ...
    def run_with_runtime(
        self,
        data_bundle: DataBundle,
        context: StrategyContext,
        runtime: StrategyRuntime,
    ) -> StrategyResult: ...
```

`build_candidate_requests()` is optional and defaults to an empty list. Override
it only for dynamic-universe strategies. `run_with_runtime()` is optional and
defaults to delegating to `run()`.

## SDK Contract 1.0 and 1.1

Contract `1.0` supports `TargetAllocationResult` end-to-end. It also supports
`StrategySignalResult` when the strategy config provides a Maestro-owned
signal-to-allocation policy. Contract `1.1` adds `StrategyRuntime` for
Maestro-backed runtime DataHub requests during `run_with_runtime()`.

Use these manifest defaults for a new wrapper:

```python
StrategyManifest(
    sdk_contract_version="1.1",
    strategy_id="my_virtuoso_app",
    name="my_virtuoso_app",
    version="0.1.0",
    supported_modes=["paper"],
    supported_asset_types=["cash", "stock", "etf", "domestic_etf", "us_etf"],
    result_type="target_allocation",
    requires_data=["price"],
    can_run_live=False,
    allow_direct_external_data_calls=False,
)
```

Set `requires_llm`, `supported_llm_providers`, `required_env_vars`,
`estimated_runtime_seconds`, and `allow_direct_external_data_calls` if the app
has LLM or external-network requirements. The current default for wrappers is to
request market and research data through Maestro DataHub instead of calling
external data APIs directly.

## Runtime Lifecycle

For each `run_once`, Maestro performs this strategy-facing sequence:

1. Load enabled plugins through the loader.
2. Build `StrategyContext` from the current run, current portfolio state, and
   `strategies[*].config`.
3. For dynamic-universe apps, call `build_candidate_requests()` and evaluate the
   candidates through Maestro universe policy.
4. Call `build_data_requests(context)`.
5. Fetch all requested data through Maestro DataHub.
6. Call `run_with_runtime(data_bundle, context, runtime)`.
7. Normalize `StrategySignalResult` to `TargetAllocationResult` when needed.
8. Validate the normalized `TargetAllocationResult`.
9. Combine strategy outputs using configured strategy weights.
10. Run risk checks, approval gates, execution, state persistence, and audit.

The app does not call these Maestro services directly. If it needs data during
analysis, it calls `runtime.get_data(DataRequest(...))`.

## StrategyContext

`StrategyContext` gives the wrapper the run metadata and user config:

- `cycle_id`: current Maestro run id
- `timestamp`: Maestro timestamp for the strategy cycle
- `run_mode`: `paper`, `live_readonly`, or `live_approval`
- `strategy_id`: configured strategy id
- `portfolio_state`: current portfolio state as JSON-like data
- `config`: app-specific config from `strategies[*].config`

Keep wrapper config explicit and small. Prefer simple data such as symbols,
allocation limits, model names, lookback values, and feature flags. Do not put
secrets directly in config; reference environment variable names when needed.

## Data Requests

Apps request data with `DataRequest`; Maestro decides which provider serves it.

Common fields:

- `symbol`: Maestro symbol
- `asset_type`: `cash`, `stock`, `etf`, `domestic_etf`, or `us_etf`
- `data_type`: such as `price`, `ohlcv`, `macro`, `news`, `sentiment`,
  `technical_indicators`, `fundamental`, or `financial_statements`
- `intended_use`: `research` or `tradable`
- `timeframe`, `lookback`, `start`, `end`, `as_of`
- `indicator`, `limit`, `query`, `statement_type`, `frequency`
- `provider_hint`, `source_hint`, `fields`

Do not import DataHub providers or normalize provider-specific payloads inside
Maestro. The wrapper may translate the returned `DataBundle.data` into the raw
input shape expected by the upstream strategy repository.

## Dynamic Universe

Use `CandidateInstrumentRequest` only when the app needs Maestro to evaluate
new research or tradable candidates.

Rules:

- Set `StrategyManifest.supports_dynamic_universe=True`.
- Set `max_candidate_symbols` to a conservative bound.
- Return candidates from `build_candidate_requests(context)`.
- Mark each candidate `intended_use` as `research` or `tradable`.
- Do not allocate to research-only symbols.

Tradable candidates must pass Maestro universe policy, operator approval,
broker tradability checks, and DataHub freshness checks before they can become
temporary or persistent tradable entries. Static `portfolio.allowed_symbols`
configs remain valid for examples, tests, and conservative paper runs.

## Wrapper Implementation Pattern

Keep upstream strategy adaptation in three explicit steps:

```python
def _to_raw_strategy_input(
    self,
    data_bundle: DataBundle,
    context: StrategyContext,
) -> dict[str, Any]:
    ...

def _run_raw_strategy(self, raw_inputs: dict[str, Any]) -> dict[str, Any]:
    ...

def _signal_to_allocations(
    self,
    raw_signal: dict[str, Any],
    context: StrategyContext,
) -> dict[str, float]:
    ...
```

This keeps the Maestro boundary visible:

- Maestro SDK data enters through `DataBundle` and `StrategyContext`.
- The upstream repository runs behind the wrapper boundary.
- The wrapper converts raw output into `TargetAllocationResult`.

Avoid hidden global state. Construct expensive upstream clients lazily only when
needed, and disclose required environment variables in the manifest.

## Target Allocation Results

Current executable apps return `TargetAllocationResult`:

```python
TargetAllocationResult(
    strategy_id=context.strategy_id,
    strategy_version=self.manifest().version,
    timestamp=context.timestamp,
    allocations={"SPY": 0.6, "CASH": 0.4},
    confidence=0.75,
    time_horizon="1-3 months",
    rationale="Short explanation for operators.",
    metadata={"raw_signal": raw_signal},
)
```

Validation rules enforced after `run()`:

- `strategy_id` must be one of the loaded strategy ids.
- Either `allocations` or `allocation_sleeves` must be non-empty.
- Allocation weights must be non-negative.
- Each allocation map must sum to `1.0` or less.
- Non-cash allocation symbols must be in the allowed tradable universe.
- Research-only symbols cannot receive allocation weight.

Use `metadata` for source signals, ratings, report summaries, tool traces, and
model details that should travel with the final allocation proposal. Do not put
secrets in metadata.

Use `allocation_sleeves` only when the app intentionally emits currency or
portfolio sleeves. If any strategy returns sleeves, Maestro builds a sleeve
target from sleeve outputs.

## App Package Rules

An app package should expose one stable `BaseStrategyPlugin` implementation
through a `module:ClassName` entrypoint.

The scaffold intentionally leaves `dependencies = []` in `pyproject.toml`.
Maestro must already be installed in the runtime environment. Add only the
upstream strategy and app-specific dependencies that the wrapper actually
needs. Keep heavy strategy dependencies in the app repo so Maestro core remains
strategy-agnostic and does not inherit optional LLM or research-framework
dependencies.

Keep the generated contract test and extend it as the wrapper grows. Tests
should verify:

- the plugin is a `BaseStrategyPlugin`
- manifest id, SDK contract version, and result type match config expectations
- data requests have the expected symbols, asset types, and data types
- `run()` returns `TargetAllocationResult`
- allocation outputs pass expected shape and weight rules
- source imports only `maestro.sdk` from Maestro
- shell environment secret values are not written into generated files,
  result metadata, logs, or test snapshots

## Common Failure Modes

`entrypoint must use 'module:ClassName' format`

The config entrypoint is missing `:` or points to the wrong module/class.

`Strategy config id ... does not match manifest id ...`

Make `strategies[*].id` and `StrategyManifest.strategy_id` identical.

`Strategy ... must implement BaseStrategyPlugin`

The loaded class does not inherit from `BaseStrategyPlugin`, or the environment
loaded a different class than expected.

`Maestro execution pipeline currently supports target_allocation results only`

Set `result_type="target_allocation"` and return `TargetAllocationResult`.

`Strategy requires unsupported Maestro SDK contract version ...`

Use `sdk_contract_version="1.1"` or lower until Maestro publishes a newer
supported contract.

`allocation symbol ... is not in allowed universe`

Add the symbol to the static universe config or use dynamic-universe candidate
requests where appropriate.

## Pre-PR Checklist

Before shipping a Virtuoso app or wrapper change:

- Run the app's `tests/test_strategy_contract.py`.
- Run `ruff format --check .`, `ruff check .`, and `pytest -q` in the app repo.
- Install the app into the Maestro environment with `uv pip install -e .`.
- Run `maestro run-once --config <paper config>` before live-readiness work.
- Confirm the app imports only from `maestro.sdk`.
- Confirm manifest live/network/LLM fields accurately disclose behavior.
- Confirm no secrets are committed, logged, or placed in result metadata.
- Keep Maestro core unchanged unless the SDK, loader, scaffold, or shared
  contract itself needs to evolve.
